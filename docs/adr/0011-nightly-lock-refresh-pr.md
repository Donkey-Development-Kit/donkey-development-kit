# ADR 0011: A green nightly opens the lock-refresh PR, and the release toolchain is locked too

- **Status:** Accepted
- **Date:** 2026-10-10
- **Issue:** #763 (part of #711). Amends [ADR 0007](0007-dependency-policy.md)
  rule 3's refresh clause.

## Context

[ADR 0007](0007-dependency-policy.md) rule 3 put PR CI on a committed lock,
`python/constraints/<combo>-py3.NN.txt`, generated by
`python scripts/compile_constraints.py`. It left two gaps that #763 tracks:

- **Nothing moves the lock.** Rule 3 says the lock is refreshed by a PR a
  maintainer opens by hand, and that no scheduled job opens it, because a
  workflow needs write access to push a branch and open a PR. In practice the
  lock only moves when someone remembers, so the PR gate drifts away from what
  users install, while the nightly (rule 4) already proves every night that
  the newest releases work.
- **The release toolchain is not locked.** `publish-pypi.yml`,
  `publish-testpypi.yml` and `ci.yml`'s `base-only` job run
  `pip install build twine` and `python -m build`. That builds in an isolated
  environment with the newest `hatchling` on PyPI, so the backend that builds
  an immutable PyPI release is whatever was newest that day. `uv`, which
  `compile_constraints.py` drives, isn't pinned either.

## Decision

1. **A green nightly opens the lock-refresh PR.** `.github/workflows/lock-refresh.yml`
   runs after every successful `Nightly matrix` run on `develop`, and on
   manual dispatch. It reruns `python scripts/compile_constraints.py` on
   `develop` and, when any file changed, force-pushes the result to the
   `bot/lock-refresh` branch and opens or updates one PR to `develop`. The
   bump PR's own CI is the gate; a maintainer merges it like any other PR.
   This replaces rule 3's "there is no scheduled job to open that PR"; the
   rest of rule 3 stands, and a maintainer can still refresh by hand.
2. **The workflow's write scopes are its own.** Only the job that pushes has
   `contents: write` and `pull-requests: write`; its `alert` job alone has
   `issues: write` and opens one `lock-refresh-failure` issue on failure
   (docs/ci.md convention 4). `tests/unit/test_ci_workflows.py` holds both.
3. **The release toolchain resolves from the lock.** The `release` dependency
   group (`build`, `twine`, `hatchling`) and the `lock` group (`uv`) get
   tool-only combos in `_COMBOS`, compiled to `constraints/release-py3.11.txt`
   and `constraints/lock-py3.11.txt`. Every `python -m build` step installs
   from the release file and passes `--no-isolation`, so it builds with the
   locked `hatchling`. `tests/unit/test_constraints_lock.py` fails a build
   step that does neither.
4. **`[build-system]` keeps a floor.** `requires = ["hatchling>=1.27"]` stays
   a floor (`§8.4`): it is what a user's build from the sdist resolves, and
   the locked version is the publish job's choice, not theirs.

### Alternatives considered

- **Dependabot or Renovate.** Rejected. Both treat `pyproject.toml` as a
  manifest and would raise the `>=` floors that rule 1 keeps at the lowest
  verified version. Both bump one pin at a time, while each constraints file
  must stay one `uv pip compile` resolution of its combo (pins bumped
  independently can be unsatisfiable together, which is what broke the first,
  merged version of the lock). Dependabot also doesn't recognise
  `python/constraints/*.txt` as a lock it can regenerate.
- **A separate cron.** Rejected: following the nightly means the refresh runs
  only on a day the newest releases passed, so a red upstream day doesn't
  produce a bump PR that is red for the same reason.
- **Pin `hatchling` in `[build-system]`.** Rejected by rule 2 of ADR 0007 and
  `§8.4`: a ceiling or `==` there binds every sdist consumer.

## Consequences

- A PR opened with the default `github.token` doesn't trigger `pull_request`
  workflows, and the repository must allow GitHub Actions to create pull
  requests. The workflow uses a `LOCK_REFRESH_TOKEN` secret when one exists;
  without it, a maintainer closes and reopens the bump PR to start CI.
  Both are repository settings, recorded in `docs/ci.md`.
- `bot/lock-refresh` belongs to the workflow and is rebuilt from `develop` on
  every run.
- A bump PR whose CI is red means the lock can't move yet. The fix is the
  same as for a red nightly (rule 4): adapt the code or wait, never add a
  ceiling.
- The `mypy` half of #763 needs no ADR: `follow_imports = "skip"` for the
  optional extras is a type-checking setting, not dependency policy.
  `tests/unit/test_house_style_config.py` keeps every extra the typecheck job
  doesn't install in that override.
