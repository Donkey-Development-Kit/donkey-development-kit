# CLI & decorators

Two on-ramps to the SDK: decorators that govern a function in one line, and a
five-command CLI for setup, diagnosis, local simulation, conformance testing,
and scanning your code for agents and tools.

## Decorators

### `@donkey.governed`

Runs a function inside a [`donkey.run()`](/telemetry) scope:

```python
@donkey.governed(team="support")
async def handle_ticket(ticket): ...
```

One decorator gives the function a run/correlation ID, cost tags, an OTel span,
and typed refusals — the four things you would otherwise set up per call site.

- Wraps **both sync and async** callables.
- Works bare (`@donkey.governed`) or parametrised
  (`@donkey.governed(team=…, project=…, env=…, enduser_id=…)`).
- Takes **no `id=`**: each call opens its own run, so unrelated calls are never
  collapsed into one correlation. When you need a specific id, use
  `donkey.run(id=…)` directly.

### `@donkey.tool`

```python
@donkey.tool
async def lookup_crm(customer_id: str) -> dict:
    """Look up a customer record by id."""
    ...
```

Marks a function as a governed tool **without changing how it's called**. It
returns the same function with a `__donkey_tool__` marker and records a
`ToolSpec` (name, qualname, signature, docstring, `is_async`) in a
process-global registry you read with `registered_tools()`. Both `ToolSpec` and
`registered_tools` are exported from `donkey_kit`.

A tool with **no docstring is rejected at decoration time** (`ValueError`) — an
undescribed tool is useless to a model and to a registry.

`@donkey.tool(approval="required", risk="financial")` gates the tool behind a
human decision: a call raises `ApprovalRequired` instead of running, and
`donkey.approvals.resolve(...)` runs it once someone approves. The approval is
client-side and advisory. See [Human-in-the-loop](/hitl).

`@donkey.tool(server="sku-manager")` attributes the tool to the MCP server it
belongs to, by that server's **service ID**: lowercase kebab-case, recorded as
`ToolSpec.server`. The ID is permanent once a service is registered, so it is
always set by you and never inferred from a module path or function name. A
tool without `server=` is reported as **unattributed**, not guessed. Anything
else raises `ValueError` at decoration time.

### `@donkey.agent`

```python
@donkey.agent(name="support-triage", skills=["triage", "draft-reply"])
async def handle(task):
    """Triage a support ticket and draft a reply for a human to send."""
    ...
```

Marks an agent entry point, again **without changing how it's called**. It
returns the same function with a `__donkey_agent__` marker and records an
`AgentSpec` (name, qualname, docstring, skills, `is_async`) that you read with
`registered_agents()`; both are exported from `donkey_kit`. `name` is the
agent's service ID, with the same kebab-case rule as `server=`. The docstring is
required, because it is the agent's description. A blank or repeated skill
raises `ValueError`.

[`donkey scan`](#donkey-scan) reads the `@donkey.tool` and `@donkey.agent`
markers, and [`donkey.serve()`](/a2a) generates its A2A agent card from the same
`@donkey.agent` record, so the scan and the card can't drift.

## The CLI

```bash
pip install "donkey-kit[cli]"
```

```bash
donkey init          # writes a commented .donkey-kit.toml, names every missing env var at once
donkey doctor        # checks creds, reaches the gateway, reports budget state
donkey mock          # the local simulator — --scenario scripts failures
donkey dev my:agent  # serves an @donkey.agent behind a simulated A2A ingress
donkey test          # a thin front end to pytest --donkey-conformance
donkey scan          # finds your agents, tools and MCP servers, without running your code
donkey publish       # registers them in Exchange; --dry-run prints the plan and sends nothing
```

### Global flags

Three global flags precede the subcommand:

```bash
donkey --config ./cfg.toml init   # write the generated config file to a non-default path
donkey --config ./cfg.toml doctor # diagnose against this project config file
donkey --env Sandbox init         # write this Anypoint environment into the generated file
donkey --json init                # machine-readable output where a command supports it
```

`--config` selects the file `init` writes or the project file `doctor` reads;
`doctor` still applies the normal per-field precedence: explicit kwargs (when
calling the config loader in code), environment variables, the named file's
local overlay, the named file, user config, then defaults. `--env` applies to
`init` only; set `ANYPOINT_ENV` for `doctor`. Other commands reject these flags
with exit `2` rather than silently ignore them.

### Exit codes

Every command exits non-zero on failure, so any of them drops into CI as a
preflight. A command that needs an optional extra (`donkey mock` → `[local]`,
`donkey test` → `[test]`, `donkey doctor` → `[llm]`) prints the exact
`pip install` line and exits `1` — never a stack trace. A command whose platform
API is not verified yet exits `3` with `blocked on verification`, so a script can
tell "blocked" from "failed".

The CLI lives in the `donkey_kit.cli` package. Earlier releases also shipped
hidden provisioning commands (`validate`, `plan`, `apply`, `drift`, `lint`,
`generate`); they were removed with the refused provisioning control plane, and
typer now rejects them as unknown commands (exit `2`).

### `donkey init`

Resolves your current configuration (env vars → config files → defaults; see
[Precedence](/reference/configuration#precedence)) and writes a **commented** `.donkey-kit.toml` with the values it
found.

- **Names every missing required field at once** — control plane *and* LLM
  proxy — using the same validation the SDK runs at call time, so `init` and a
  real request never disagree about what is required.
- **Never writes a secret.** `client_secret`, `llm_proxy_client_secret`, and
  `llm_proxy_key` are emitted as commented pointers, not values. Put them in a
  gitignored `.donkey-kit.local.toml` next to the file, or in environment
  variables. A URL in `.donkey-kit.toml`, including a loopback one, only
  receives credentials from those two files unless you opt in; see
  [Which credentials a URL receives](/reference/configuration#which-credentials-a-url-receives).
  The file's comments also say that URLs must use `https://`, that `localhost`
  is accepted over plain `http://`, and that `DONKEY_ALLOW_HTTP=1` in the
  environment (not in the file) allows plain `http://` to other hosts.
- **Idempotent.** An existing file is left untouched unless you pass `--force`.

```bash
donkey init --force
donkey --json init    # {"path": "...", "written": true, "missing": [...]}
```

### `donkey doctor`

A governed call can fail for several reasons that look identical from the
outside. `doctor` makes one real governed call and tells them apart:

- **Wrong credentials** — the `client_id`/`client_secret` pair is rejected.
- **Wrong URL** — the gateway answers, but no proxy is deployed on that base
  path: an empty `404` with no `x-llm-proxy-*` headers. The `gateway` line
  fails and `credentials` and `model` show as not checked. A typo in the path,
  a trailing `/v1` (the governed proxy has no `/v1` segment), or a proxy that
  is not Active in API Manager all land here.
- **Credentials fine, model not in the allow-list** — nothing is misconfigured;
  your platform team has not granted that model.
- **`/responses` not served on this route** — the proxy accepted the
  credentials and routed the model, but the upstream answered the Responses API
  with `404`. An Azure OpenAI route does this. `doctor` then tries
  `/chat/completions` once and reports the route as working if that answers.
  Call it with `client.chat.completions.create(...)` on `donkey.llm.client()`,
  or with your framework's chat-completions client.

Each verdict prints the same remediation string the matching typed exception
carries, so the fix is in the output rather than in a runbook. The budget line
states how old the reading is, since the proxy has no budget endpoint.

Before the call, `doctor` prints each endpoint's host and where it came from:
`env`, `project file`, `local overlay`, `user file` or `default`. If the LLM
proxy URL comes from the working directory's config files but its credentials
don't (a loopback URL such as the simulator's included), the `config` line
fails with the
[remediation](/reference/configuration#which-credentials-a-url-receives) and no
request is sent. A control-plane endpoint with the same problem shows its
remediation on the `control plane` line without failing the report, since
`doctor` only calls the LLM proxy. In `jwt` mode, an LLM proxy URL from those
files always fails the `config` line, because the JWT never comes from a file:
set the URL in the environment or opt in.

With `DONKEY_ALLOW_HTTP` on in the environment, a `plain http` line says so and
quotes the value as set, for example `DONKEY_ALLOW_HTTP=true` (in `--json`
output, the entry with `"name": "plain http"`):

```text
[i]  plain http     allowed to non-loopback hosts (DONKEY_ALLOW_HTTP=1 in env)
```

```bash
donkey doctor
donkey --config ./cfg.toml doctor  # read cfg.toml and its adjacent local overlay
```

### `donkey mock`

Runs the [local simulator](/simulator), which replays captured gateway
rejections. Needs the `[local]` extra.

```bash
donkey mock --port 8080 --host 127.0.0.1 \
  --scenario pii_block:every=5 \
  --scenario budget:limit=20000,window=60s \
  --scenario request_limit:limit=3,window=60s
```

The flags are listed in the [command reference](#command-reference). The
`--scenario` rule syntax is in [Scenario scripting](/simulator#scenario-scripting).

The port isn't read from an environment variable or `.donkey-kit.toml`; these
flags (or the `serve()` keyword arguments) are the only way to change it. See
[Choosing a port or host](/simulator#choosing-a-port-or-host) for the
programmatic entry point and the `0.0.0.0` caveat.

An invalid `--scenario` exits with code `2`.

### `donkey dev`

Serves a `@donkey.agent` handler over A2A behind a simulated gateway ingress,
which rejects inbound calls with the simulator's fixtures. Needs the `[a2a]`
and `[local]` extras.

```bash
donkey dev my_agent:handle --port 8000 --scenario pii_block:every=5
```

`TARGET` is `module:attribute`, imported from the current directory. The
ingress, the rules it takes and where its rejection shapes come from are in
[Simulated ingress](/a2a#simulated-ingress). A target that can't be loaded or
isn't marked with `@donkey.agent`, and an invalid `--scenario` (including
`budget`), exit with code `2`.

### `donkey test`

A thin front end to `pytest --donkey-conformance` — it does not re-implement the
runner. Point it at your agent factory and pass any trailing pytest arguments
straight through; pytest's exit code becomes `donkey test`'s own. Needs the
`[test]` extra.

```bash
donkey test --agent my.pkg:make_agent -k governance -x
donkey test --agent my.pkg:make_agent --donkey-mode server   # over a real port; needs [local]
```

See [Testing & conformance](/testing) for what the suite checks.

### `donkey scan`

Reads your repository's source and reports every `@donkey.agent`, every
`@donkey.tool`, and the MCP servers those tools name with `server=`. The scan is
**static**: it parses each `.py` file and never imports or runs it, so a module
with side effects at import time is safe to scan. It needs no extra and no
credentials, and it writes no file.

```
$ donkey scan .
  agent  support-triage  (app/main.py:13)
  mcp    sku-manager  (1 tool: lookup_sku)  streamable-http https://sku-manager.acme.com/mcp
  unattributed  issue_refund  (set @donkey.tool(server=...))
found 1 agent, 2 tools, 1 MCP server
1 issue
  app/main.py:9  tautological  tool issue_refund: description equals identifier 'issue_refund'
```

- A marker counts only when its receiver is a `Donkey`: the class imported from
  `donkey_kit`, an instance built with `Donkey(...)` or `Donkey.from_env()`, or
  such an instance imported from another module in the repository. Other
  frameworks' `@mcp.tool()` decorators are ignored.
- Decorator arguments are read only when they are **literals**.
  `server=SERVER_ID` is reported as a `non-literal-argument` issue rather than
  guessed.
- A tool without `server=` is listed as **unattributed**. Scan never infers a
  server from a module or function name.
- How each MCP server is reached, its transport and endpoint, comes from a
  `[donkey.mcp_servers.<id>]` table in `.donkey-kit.toml`, never from code. A
  server without one is shown as `transport undeclared`, which is not an issue.
  See [Declaring how an MCP server is reached](/publishing#declaring-how-an-mcp-server-is-reached).
- An agent's protocol and endpoint come the same way from a
  `[donkey.agents.<name>]` table. See
  [Declaring how an agent is reached](/publishing#declaring-how-an-agent-is-reached).
- Issues cover a missing, tautological or too-short description, an invalid
  service ID or skill list, a service ID used twice, two tools with the same
  name on one server, a file that fails to parse, and an invalid
  `[donkey.mcp_servers]` or `[donkey.agents]` declaration. `donkey scan` exits `1`
  when it finds any of them, so it works as a CI gate, `0` when there are none,
  and `2` when the path does not exist.

`donkey scan --json` (or the global `donkey --json scan`) prints the model as
canonical JSON: keys and entries are sorted and paths are relative, so the same
code always gives the same bytes and a CI diff shows only real changes. The
`digest` field hashes what would be published and leaves out file paths and
line numbers, so moving code around does not change it.

Scan is the first half of [Scan & publish](/publishing): the model it builds is
the input `donkey publish` reads.

### `donkey publish`

```bash
donkey publish --dry-run .   # the assets a publish would register; no network call
donkey publish .             # publish the MCP servers and agents that changed
```

Registers each MCP server and agent that `donkey scan` finds as an Exchange
asset, in the group and at the version declared in `[donkey.publication]`. An
asset whose latest published version has the same digest is left unchanged;
one changed without a version bump is refused before anything is published. It reads
the `ANYPOINT_*` control-plane credentials, and exits `0` when everything was
published or left unchanged, `1` on an issue or a refused publish, and `2` on a
missing path, invalid config or missing credentials. See
[Scan & publish](/publishing#planning-a-publish).
