# A2A agents

<Callout type="info">
  **Phase 2 — designed, not yet shipped.** Command and API shapes below are a
  proposal; the committed part is the behaviour. See [Roadmap](/roadmap) and
  [Verification policy](/concepts/verification).
</Callout>

Three commands that take an agent from "runs on my laptop" to "callable by
other agents, through the gateway."

## First, an honest answer to the obvious question

The question that always comes up: *A2A needs an HTTP listener — we have the
gateway, so can the gateway ingress be embedded in the agent process, making
the agent A2A-ready without running its own server?*

**No to the literal idea, yes to what it is really asking for.**

Omni Gateway is an Envoy-based data plane whose policies compile to WASM. It is
a separate process, not a library — you cannot `import` it any more than you
could import nginx. More importantly you would not want to:

<Callout type="warning">
  **The moment the enforcement point lives inside the agent's process, the
  agent's own code can bypass it.** The gateway's value depends on being
  *outside* the thing it governs.
</Callout>

So be precise about what A2A actually requires: something must accept the
socket. An A2A agent *is* a server — it serves an agent card at a well-known
path and answers JSON-RPC task calls. That listener can be hidden behind one
line, but it cannot be removed.

What *can* be removed is everything painful about it: TLS, auth, rate limits,
public exposure, and registration. Those are the gateway's job, and that is
where the SDK helps.

## `donkey serve` — the listener, in one line

```python
@donkey.agent(name="support-triage", skills=["triage", "draft-reply"])
async def handle(task: A2ATask) -> A2AResult:
    return await graph.ainvoke(task.input)

donkey.serve(handle)      # A2A server on 127.0.0.1:8000, card auto-generated
```

The card is generated from the same `@donkey.tool` / `@donkey.agent` markers
the [scanner](/publishing) reads, so there is no second description of your
agent to keep in sync. It binds to **localhost by default** — your agent is
never the public face.

The protocol itself is the official **`a2a-sdk`**, wrapped. This project does
not implement A2A; re-implementing a protocol someone else maintains is on the
[will-not-build list](/roadmap).

What a plain A2A server does *not* give you is the inbound governance path:
every call arriving over A2A gets the same treatment as an outgoing one —
correlation ID, cost tags, an OTel span, and typed refusals when the agent's
own downstream calls are blocked.

## `donkey expose` — the ingress, registered from code

```
$ donkey expose --env prod
  ✓ A2A proxy  https://gw.acme.internal/agents/support-triage
  ✓ policies   token-budget, pii-detection, trusted-agent-identity
  ✓ registry   support-triage v1.4.0
```

The gateway does the work — provisioning the A2A proxy, attaching the policy
set, registering the card. The SDK's contribution is turning a console session
into one command that runs in CI.

## `donkey dev` — a gateway in front of your laptop

Two options, and which one ships depends on what is actually available rather
than on preference:

- **A real gateway.** If a self-managed Omni Gateway image is usable for local
  development, `donkey dev` runs it alongside `donkey serve` so you hit A2A
  *through real policies* on your machine. Gated on image availability and
  licensing.
- **Simulated ingress.** If that is blocked, the [local simulator](/simulator)
  gains an A2A ingress mode: a local fake gateway in front of `donkey serve`,
  replaying the same rejection fixtures. Fully within this project's control,
  and held to the same honesty test — a plain A2A client must see
  byte-identical responses.
