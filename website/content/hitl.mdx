# Human-in-the-loop

Refunds over €100 need a human. Without a shared vocabulary that is bespoke
code in every team and every framework. With DDK you declare the requirement
on the tool itself:

```python
from donkey_kit import Donkey

donkey = Donkey()


@donkey.tool(approval="required", risk="financial")
async def issue_refund(ticket_id: str, amount: float) -> str:
    """Refund a support ticket."""
    ...
```

Calling `issue_refund` does not run it. DDK records a pending approval, emits
it on a span, and raises `ApprovalRequired`. Your code gets a decision from a
human, wherever it already asks for one, then resumes the call:

```python
from donkey_kit import ApprovalRequired, Donkey

donkey = Donkey()


async def handle(ticket_id: str, amount: float) -> None:
    try:
        await issue_refund(ticket_id, amount)
    except ApprovalRequired as err:
        # Show err.tool, err.arguments and err.risk to a reviewer: a Slack
        # message, a ServiceNow ticket, your own UI.
        ask_a_reviewer(err.approval)


async def on_decision(approval_id: str, reviewer: str, approved: bool) -> None:
    if approved:
        await donkey.approvals.resolve(approval_id, approved_by=reviewer)
    else:
        donkey.approvals.reject(approval_id, rejected_by=reviewer)
```

<Callout type="warning">
  **The approval is advisory.** It runs in your process, before the call. The
  gateway does not know that an approval was needed or who gave it, and
  nothing stops code that skips the decorator. Routing a high-risk approval
  through the gateway's identity layer (step-up) is on the
  [Roadmap](/roadmap). Until then, treat the approval as an audit record of
  your own process, not as an enforcement point.
</Callout>

## Declaring an approval

`@donkey.tool` takes three optional keywords. Bare `@donkey.tool` is unchanged:
it marks the tool and returns the same function (see
[CLI & decorators](/cli#donkeytool)).

| Keyword | Default | Meaning |
|---|---|---|
| `approval` | `None` | `"required"` gates the tool behind a human decision. |
| `risk` | `None` | A label you choose, such as `"financial"`. DDK carries it on the approval and the span, and attaches no behaviour to it. |
| `approval_timeout` | `"15m"` | How long a pending approval waits for a decision: seconds, a `timedelta`, or a string such as `"30s"`, `"15m"` or `"1h"`. |

A gated tool keeps its name, docstring, signature and `async`-ness, so a
framework that introspects tools sees the original. `registered_tools()`
records `approval` and `risk` on its `ToolSpec`, and the `ToolSpec`'s `func` is
the gated function.

The call's arguments are checked against the signature before anything is
recorded. A call that could never run raises `TypeError` straight away instead
of waiting for a reviewer.

## What `ApprovalRequired` carries

`ApprovalRequired` is a `DonkeyError`, but not a `PolicyViolation`. No gateway
refused anything, and the [refusal handlers](/refusal-handlers) never see it.
`err.approval` is the pending call, an `Approval`:

| Field | What it holds |
|---|---|
| `id` | The id you pass to `resolve` or `reject`. |
| `tool` | The tool's name. |
| `arguments` | The call's arguments by parameter name, defaults included, as a read-only mapping. |
| `risk` | The `risk=` the tool declared, or `None`. |
| `correlation_id` | The enclosing `donkey.run()` id, or a fresh one outside a run. |
| `requested_at`, `expires_at` | Unix timestamps. `expired` is true once `expires_at` has passed. |

`err.tool`, `err.arguments`, `err.risk` and `err.correlation_id` are shortcuts
to the same values. The exception's message names the tool and the approval id,
never the arguments.

## Resolving

`donkey.approvals` is the process's registry of pending approvals. Every
`Donkey` in the process returns the same one.

- `resolve(id, approved_by=...)` records the approver and runs the tool with
  the arguments it was called with. It returns what the tool returns. For an
  `async` tool that is an awaitable, so `await` it.
- `reject(id, rejected_by=...)` records who refused and drops the call without
  running it. It returns the `Approval`, so you can tell the agent.
- `pending()` lists the approvals still waiting, oldest first. `get(id)`
  returns one.

`approved_by` and `rejected_by` must be non-empty. Each approval is decided
once: resolving or rejecting an id that is no longer pending raises
`KeyError`. DDK records the name you pass and does not authenticate it.

The resumed call runs under the approval's `correlation_id`, not the
correlation of the code that resolves it. So the gateway's records for every
model call the tool makes join to the approval, however much later the
decision arrives.

### An approval never overrides a refusal

The resumed tool goes through the governed transport like any other code. The
gateway judges every model call it makes afresh, and a refusal is raised as
usual: typed inside `donkey.run()` or `@donkey.governed`, and seen by your
refusal handlers. An approval says a human allowed the tool to run. It does
not say the gateway has to accept what the tool sends.

## Timeouts

A pending approval waits `approval_timeout` (15 minutes unless the tool sets
one). After that, `resolve` and `reject` raise `ApprovalTimedOut`, and the call
is not made. `pending()` drops expired approvals. Nothing in DDK waits on a
human, so an unanswered approval never hangs your agent. Call the tool again
to ask for a fresh decision.

A pause that [LangGraph holds](#in-a-langgraph-graph) has no timeout: it waits
in the checkpointer until the graph is resumed, and `approval_timeout` does not
apply.

## The audit trail

Each step of an approval is a short `donkey.tool.approval` span, a child of
whatever span is current, with one event:

| Event | Extra attribute |
|---|---|
| `donkey.approval.pending` | `donkey.approval.expires_at`, unless LangGraph holds the pause |
| `donkey.approval.approved` | `donkey.approval.approved_by` |
| `donkey.approval.rejected` | `donkey.approval.rejected_by` |
| `donkey.approval.timed_out` | — |

Every event also carries `gen_ai.tool.name`, `donkey.approval.id`,
`donkey.correlation_id` and, when the tool declared one,
`donkey.approval.risk`. So "who approved this refund?" is a query on the
correlation ID. Each decision and timeout is also logged at `INFO` on the
`donkey_kit.core.approvals` logger.

The tool's arguments never go on a span or into a log record. They are request
content, the same content that [stays off spans](/telemetry#message-content-stays-off-spans-by-default)
for model calls. Show them to the reviewer from `err.arguments`.

Approval spans go to the same tracer as DDK's other spans (see
[Telemetry & cost](/telemetry)). A decorator has no `Donkey` configuration to
read, so `DONKEY_TELEMETRY=false` does not stop them reaching a
`TracerProvider` your process installed itself.

## Pending approvals live in memory

The registry is in-process memory. A restart forgets every pending approval,
and resolving one after a restart raises `KeyError`. When a pause has to
survive a restart, use a framework's own durable pause, such as LangGraph's
checkpointer or the OpenAI Agents SDK's serialised `RunState` (see below).

## In a LangGraph graph

Inside a LangGraph graph that runs with a checkpointer and a `thread_id`, a
gated tool does not raise `ApprovalRequired`. It pauses with LangGraph's own
`interrupt()`, from a plain node or from a `ToolNode`, and you resume it with
`Command(resume=...)`. Nothing changes on the tool:

```python
from donkey_kit import Donkey
from langgraph.checkpoint.memory import MemorySaver
from langgraph.graph import END, START, StateGraph
from langgraph.types import Command

donkey = Donkey()


@donkey.tool(approval="required", risk="financial")
def issue_refund(ticket_id: str, amount: float) -> str:
    """Refund a support ticket."""
    return f"refunded {ticket_id}"


def refund(state: dict) -> dict:
    return {"result": issue_refund(state["ticket_id"], state["amount"])}


builder = StateGraph(dict)
builder.add_node("refund", refund)
builder.add_edge(START, "refund")
builder.add_edge("refund", END)
graph = builder.compile(checkpointer=MemorySaver())
thread = {"configurable": {"thread_id": "ticket-T-1"}}

paused = graph.invoke({"ticket_id": "T-1", "amount": 140.0}, thread)
request = paused["__interrupt__"][0].value  # show this to a reviewer

done = graph.invoke(Command(resume={"approved": True, "by": "m.keller"}), thread)
```

The interrupt's value describes the call:

| Key | What it holds |
|---|---|
| `type` | `"donkey.approval"`, so you can tell it from your own interrupts. |
| `approval_id` | The approval's id, the same one on its span events. |
| `tool`, `arguments`, `risk` | As on an `Approval`. `arguments` is a plain `dict`. |
| `correlation_id` | The enclosing `donkey.run()` id, or a fresh one outside a run. |

Resume with `{"approved": True, "by": "<approver>"}` to record the approver and
run the tool, or `{"approved": False, "by": "<approver>"}` to refuse it. A
refused call raises `ApprovalRejected` from the tool, which carries the
`Approval`; a `ToolNode(handle_tool_errors=True)` turns it into a tool message
for the model. Any other resume value raises `ValueError`. `by` must be a
non-empty string, and DDK records it without authenticating it.

The pause lives in your checkpointer, not in `donkey.approvals`: `pending()`
does not list it, and `resolve` and `reject` do not apply to it. A durable
checkpointer keeps it across a restart. A fresh process with the same graph and
thread resumes it, and the approval id joins the pending and approved events
because DDK derives it from the thread, the tool and the arguments. The
interrupt's value, arguments included, is stored by your checkpointer like the
rest of the graph's state.

A refusal and the pause compose. A model call refused before the gated tool
raises typed, and no approval is requested. A model call the approved tool
makes is judged by the gateway as usual, and its refusal leaves the graph
typed.

<Callout type="warning">
  **LangGraph re-runs a node from its start on resume.** If one node calls two
  gated tools, or the model asks for two in one turn, LangGraph pauses for each
  in turn, and resuming the second runs the first approved tool again. Give the
  model one gated call per turn (for example `parallel_tool_calls=False`), or
  make the tool safe to repeat.
</Callout>

The resumed tool runs under the correlation id of the `donkey.run()` that
resumes the graph, or the pause's own outside a run. To join the gateway's
records to the pause, resume under the same run id you paused under.

Two cases fall back to the raise-and-resume form above, with
`ApprovalRequired` raised out of the graph: a graph compiled without a
checkpointer, which has no thread to resume, and, on Python 3.10, a graph run
with `ainvoke()`, where LangGraph cannot see the run's config from inside the
tool (see [LangGraph](/frameworks/langgraph#interrupt-composes-with-typed-refusals)).

## In an OpenAI Agents SDK run

The OpenAI Agents SDK has its own tool approval: a `FunctionTool` with
`needs_approval` stops `Runner.run` before the tool runs and returns the call in
`result.interruptions`. Build the agent's tool with
`donkey_kit.integrations.openai_agents.function_tool`, and a gated
`@donkey.tool` sets it for you:

```python
from agents import Agent, Runner
from donkey_kit import Donkey
from donkey_kit.integrations import openai_agents

donkey = Donkey()


@donkey.tool(approval="required", risk="financial")
def issue_refund(ticket_id: str, amount: float) -> str:
    """Refund a support ticket."""
    return f"refunded {ticket_id}"


agent = Agent(
    name="refunds",
    model=donkey.openai_agents.model("gpt-4o"),
    tools=[openai_agents.function_tool(issue_refund)],
)

async with donkey.run(id="ticket-T-1"):
    result = await Runner.run(agent, "Refund ticket T-1")
    (approval,) = openai_agents.pending_approvals(result)  # show this to a reviewer

state = result.to_state()
async with donkey.run(id=approval.correlation_id):
    openai_agents.approve(state, approval, by="m.keller")
    done = await Runner.run(agent, state)
```

`pending_approvals(result)` returns an `Approval` for each paused call to a
gated tool and records its pending span event. It skips interruptions it did
not gate, so your own `needs_approval` tools are left to you. `approve(state,
approval, by=...)` records the approver and approves the call on the
`RunState`, and the next `Runner.run(agent, state)` runs the tool once.
`approve` and `reject` also take the approval's id, and raise `KeyError` for an
id with no paused call in the state. A call is decided once: a second `approve`
or `reject` of it on the same `RunState` raises `KeyError` and records nothing.
DDK remembers the decisions on each `RunState` object, so decide on the state you
resume, because each `result.to_state()` builds a new one. Passed an `Approval`,
the decision keeps its correlation id, so it joins the pending event even when
you decide outside the `donkey.run()` that paused. `by` must be a non-empty
string, and DDK records it without authenticating it.

`reject(state, approval, by=..., message=None)` records the rejecter and
rejects the call. The tool does not run, and the run goes on: the Agents SDK
hands the model `message`, or a default that names the tool, as the tool's
result. It does not raise `ApprovalRejected`, and the rejecter's name never
reaches the model.

The pause lives in the `RunState`, not in `donkey.approvals`. It survives
`state.to_string()` and `RunState.from_string(agent, ...)`, and the approval id
joins the pending and approved events because DDK derives it from the call id,
the tool and the arguments. Decide through `approve` and `reject`: calling
`RunState.approve` yourself runs the tool with no approver on record, and DDK
does not offer the SDK's `always_approve` or `always_reject`, which would let
later calls run with no decision recorded.

The resumed tool runs under the correlation id of the `donkey.run()` that
resumes the run, or the approval's own outside a run. A model call the approved
tool makes is judged by the gateway as usual, and its refusal leaves
`Runner.run` typed instead of becoming a tool result.

Wrap a gated tool with the DDK `function_tool`, not the SDK's own
`agents.function_tool`. The SDK's own wrapper does not pause: the gate raises
`ApprovalRequired`, and the SDK hands it to the model as a tool-result string.
The DDK `function_tool` refuses a `needs_approval` keyword for a gated tool, and
if the SDK's approval is switched off on the built tool, `ApprovalRequired`
leaves `donkey.run()` typed and the tool does not run.

## In a Strands agent

A Strands agent pauses a gated tool with Strands' own interrupt once you give
it an `ApprovalHook`. The hook raises the interrupt from `BeforeToolCallEvent`,
before the tool runs, and the agent stops with `stop_reason == "interrupt"`.
Wrap the gated function in Strands' `tool()` as you would any other:

```python
from donkey_kit import Donkey
from donkey_kit.integrations.strands import ApprovalHook, approve, pending_approvals, reject
from strands import Agent, tool

donkey = Donkey()


@donkey.tool(approval="required", risk="financial")
def issue_refund(ticket_id: str, amount: float) -> str:
    """Refund a support ticket."""
    return f"refunded {ticket_id}"


agent = Agent(
    model=donkey.strands.model("gpt-4o"),
    tools=[tool(issue_refund)],
    hooks=[ApprovalHook()],
)

result = await agent.invoke_async("Refund ticket T-1, 140 euros")
if result.stop_reason == "interrupt":
    requests = pending_approvals(result)  # show each one's .reason to a reviewer
    result = await agent.invoke_async([approve(r, by="m.keller") for r in requests])
```

`pending_approvals(result)` returns the paused calls, which are Strands' own
`Interrupt` objects named `"donkey.approval"`. Each one's `reason` describes the
call:

| Key | What it holds |
|---|---|
| `approval_id` | The approval's id, the same one on its span events. |
| `tool`, `arguments`, `risk` | As on an `Approval`. `arguments` is a plain `dict`. |
| `correlation_id` | The enclosing `donkey.run()` id, or a fresh one outside a run. |

Resume the agent on a list of responses, one for each paused call:

- `approve(request, by=...)` records the approver and runs the tool once,
  under the approval's correlation id, wherever and whenever you resume.
- `reject(request, by=..., message=...)` records who refused, and the tool is
  not run. Strands sends the model `message` as an error tool result, or a
  default that names the tool, never the rejecter. Nothing raises `ApprovalRejected`:
  the model reads the rejection and carries on.

`by` must be a non-empty string, and DDK records it without authenticating it.
Each paused call is decided once, even if another hook retries the tool. When
the model asks for several gated calls in one turn, Strands' default concurrent
executor pauses them together, and a `SequentialToolExecutor` pauses on each in
turn.

Strands holds the pause, not `donkey.approvals`: `pending()` does not list it,
and `approval_timeout` does not apply. The approval id is derived from Strands'
tool-use id, the tool and the arguments. To resume a call in a fresh process
that restored the agent from a Strands session, give the restored agent a new
`ApprovalHook`. The decision is then recorded under the same approval id, with
the resume's time and correlation id.

A model call the approved tool makes is judged by the gateway as usual. Strands
hands any exception a tool raises to the model as an error tool result,
refusals included, so a refusal from inside the tool does not leave the agent.

Without the hook, nothing pauses. The gate raises `ApprovalRequired` inside the
tool, Strands turns it into an error tool result, and the call waits in
`donkey.approvals` like any other.

## In a Google ADK app

An ADK app pauses a gated tool with ADK's own tool confirmation once you add
the plugin `approval_plugin()` builds. Before the tool runs, the plugin asks
ADK for a confirmation, and the run ends its turn with an
`adk_request_confirmation` call. List the gated function in the agent's
`tools` as you would any other:

```python
from donkey_kit import Donkey
from donkey_kit.integrations.adk import approval_plugin, approve, pending_approvals, reject
from google.adk.agents import LlmAgent
from google.adk.apps import App
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types

donkey = Donkey()


@donkey.tool(approval="required", risk="financial")
def issue_refund(ticket_id: str, amount: float) -> str:
    """Refund a support ticket."""
    return f"refunded {ticket_id}"


agent = LlmAgent(name="refunds", model=donkey.adk.model("gpt-4o"), tools=[issue_refund])
app = App(name="refunds", root_agent=agent, plugins=[approval_plugin()])
sessions = InMemorySessionService()
runner = Runner(app=app, session_service=sessions)
session = await sessions.create_session(app_name="refunds", user_id="u")


async def send(message: types.Content) -> list:
    run = runner.run_async(user_id="u", session_id=session.id, new_message=message)
    return [event async for event in run]


events = await send(types.Content(role="user", parts=[types.Part(text="Refund T-1, 140 euros")]))
requests = pending_approvals(events)  # show each one's payload to a reviewer
if requests:
    answer = types.Content(role="user", parts=[approve(r, by="m.keller") for r in requests])
    events = await send(answer)
```

`pending_approvals(events)` returns the unanswered requests among the events
you pass it: the run's events, or a session's `events`. Each is ADK's own
`adk_request_confirmation` function call. Its
`args["toolConfirmation"]["payload"]` describes the call:

| Key | What it holds |
|---|---|
| `kind` | `"donkey.approval"`, so you can tell a DDK approval from other confirmations. |
| `approval_id` | The approval's id, the same one on its span events. |
| `tool`, `arguments`, `risk` | As on an `Approval`. `arguments` holds the arguments as the model sent them. |
| `correlation_id` | The enclosing `donkey.run()` id, or a fresh one outside a run. |

Resume the run with one user message whose parts answer the requests:

- `approve(request, by=...)` records the approver and runs the tool once,
  under the pause's correlation id, wherever and whenever you resume.
- `reject(request, by=..., message=...)` records who refused, and the tool is
  not run. The model gets `message` as the tool's error result, or a default
  that names the tool, never the rejecter. Nothing raises `ApprovalRejected`:
  the model reads the rejection and carries on.

`by` must be a non-empty string, and DDK records it without authenticating it.
ADK keeps the confirmation calls and their answers out of the model's context,
so the approver's name never reaches the model.

ADK holds the pause, not `donkey.approvals`: `pending()` does not list it, and
`approval_timeout` does not apply. The pause lives in the session's events, so
a fresh process with a fresh plugin can resume it from any persistent
`SessionService`. The approval id is derived from ADK's function-call id, the
tool and the arguments as sent, so the decision is recorded under the same id
and joins the pause's correlation id.

A model call the approved tool makes is judged by the gateway as usual. An
exception the tool raises, a refusal included, leaves the runner as any tool
exception does in ADK.

Without the plugin, nothing pauses. The gate raises `ApprovalRequired` inside
the tool, which leaves the runner, and the call waits in `donkey.approvals`
like any other.

## Discovered tools <Badge tone="roadmap">Roadmap</Badge>

`@donkey.tool` decorates a local function. A governed MCP tool from
[`donkey.tools.discover()`](/tool-access/discovery) is not one, so you declare
its approval once on the `ToolSet` instead. Tool discovery and binding are on
the [Roadmap](/roadmap), so this section shows the planned design:

```python
# `tools` is the ToolSet that donkey.tools.discover() returns, before you bind it.
tools = tools.require_approval(tools=["issue_refund", "void_invoice"], risk="financial")
```

A call to a gated tool behaves exactly like a gated `@donkey.tool`: it raises
`ApprovalRequired`, or pauses a LangGraph graph with `interrupt()`, records the
same span events, and resolves through `donkey.approvals`. `Approval.arguments`
holds the tool's arguments by name, taken from its input schema.

| Keyword | Default | Meaning |
|---|---|---|
| `tools` | — | Exact tool names to gate. |
| `risk` | `None` | A label for the reviewer and the span, as on `@donkey.tool`. |
| `timeout` | `"15m"` | How long a pending approval waits, as `approval_timeout` on `@donkey.tool`. |

- **Names are exact,** like [`filter()`](/tool-access/binding#mcp-session-management).
  A bare name such as `"issue_refund"` gates that tool on every server in the
  set. The server-prefixed name collision resolution exposes, such as
  `"billing__issue_refund"`, gates only that server's tool.
- **A typo fails at bind time.** Binding raises `ConfigError` for a name that no
  server in the set exposes, so a misspelt name can never leave a tool ungated.
  Removing a gated tool with `filter()` is fine.
- **Rules accumulate.** Each call returns a new `ToolSet`, `filter()` keeps the
  rules, and when two rules name the same tool the later one sets its `risk`
  and `timeout`.

The approval is advisory here too, for the same reason as above: the gateway
does not know it was needed until step-up routes it through the gateway.

## Mapped onto what your framework already has

DDK does not introduce a new pause mechanism. The raise-and-resume form above
works in any Python code, and LangGraph's own `interrupt()`, the OpenAI Agents
SDK's `needs_approval`, Strands' interrupt hooks and Google ADK's tool
confirmation are mapped. Gateway step-up is planned:

| Framework / protocol | Native primitive | Status |
|---|---|---|
| Any Python code | `ApprovalRequired` + `donkey.approvals.resolve(...)` | <Badge tone="live">Live</Badge> |
| LangGraph | `interrupt()` / `Command(resume=…)` | <Badge tone="live">Live</Badge> |
| OpenAI Agents SDK | `needs_approval` / `RunState.approve(…)` | <Badge tone="live">Live</Badge> |
| Google ADK | tool confirmation, via `approval_plugin()` | <Badge tone="live">Live</Badge> |
| Strands | `BeforeToolCallEvent` interrupt, via `ApprovalHook` | <Badge tone="live">Live</Badge> |
| MCP | elicitation | <Badge tone="neutral">Not supported</Badge> |
| Omni Gateway | Trusted Agent Identity step-up (MFA) | <Badge tone="roadmap">Roadmap</Badge> |

MCP elicitation is not a client-side approval, so DDK does not map onto it. A
server sends `elicitation/create` to ask the user something while it handles a
request. The direction is server to client, so a client cannot use it to hold a
call it is about to send, and there is nothing for it to pause or resume.
Governed MCP tools get their approval from
[`require_approval()`](#discovered-tools-roadmap) on the `ToolSet` instead, which gates
the call before it leaves the client once binding ships.

## What DDK does not build

<Callout type="info">
  DDK will not ship an approval queue or an approval UI. Both are on the
  [will-not-build list](/roadmap). It integrates with whatever you already
  run: Slack, ServiceNow, or LangGraph's own checkpointer.
</Callout>

Specifically, DDK does not:

- store approvals durably, or share them between processes;
- notify a reviewer, escalate an unanswered approval, or retry one that timed
  out;
- decide who may approve, or authenticate the `approved_by` you pass;
- tell the gateway that a call was approved.

A queue would mean owning a durable store, an escalation model and a
notification system: a product rather than a feature.
