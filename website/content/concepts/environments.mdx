# Governance & environments

<Callout type="info">
  **Planned design.** This documents SDK behaviour as designed in the build plan; platform contracts it depends on are being live-verified, and unverified paths raise `NotImplementedError("blocked on verification: …")` rather than guess. See [Verification policy](/concepts/verification).
</Callout>

The [`Governance`](/concepts/governance) object is the single thing an agent
declares once. What changes across local, sandbox, and production is not the
object — it's which of its three verbs you call, and what a gateway can
actually enforce on your laptop versus a shared control plane.

## The `Governance` object

```python
from donkey_kit import Governance, GatewayTarget, PolicyBinding

gov = Governance(
    name="hr-agent",
    gateway=GatewayTarget.from_env(),      # resolves local | sandbox | prod
    policies=[
        PolicyBinding("rate-limiting-sla-based", "1.4.0", config={
            "rateLimits": [{"maximumRequests": 100, "timePeriodInMilliseconds": 60000}],
        }),
        PolicyBinding("openai-token-policy", "1.0.0", config={
            "maxTokensPerMinute": 50_000,
        }),
        PolicyBinding("prompt-injection-protection", "1.0.0"),
    ],
)
```

The same object attaches wherever a model or a tool is constructed:

```python
model = donkey.langgraph.chat_model("gpt-4o", governance=gov)
tools = await donkey.tools.discover(domain="hr", governed_only=True, governance=gov)
```

### `GatewayTarget` — the environment-varying part

```python
@dataclass(frozen=True)
class GatewayTarget:
    mode: Literal["local", "managed", "self-managed"]
    base_url: str                    # http://localhost:8081 | https://<managed>.gw... | https://<own-host>
    environment: str | None = None   # None for local
    gateway_name: str | None = None  # control-plane gateway/registration name
    connected: bool = True           # local mode gateways are unconnected

    @classmethod
    def from_env(cls) -> "GatewayTarget":
        """DONKEY_TARGET=local|sandbox|production selects a profile from
        .donkey-kit.toml. Local requires no Anypoint credentials beyond
        whatever registration the local gateway itself needs."""
```

Profiles live in `.donkey-kit.toml`, committed to the repo — the same
pattern as Terraform workspaces or Kustomize overlays:

```toml
[targets.local]
mode = "local"
base_url = "http://localhost:8081"

[targets.sandbox]
mode = "managed"
base_url = "https://hr-agent.sandbox.eu1.gw.mulesoft.com"
environment = "Sandbox"
gateway_name = "managed-omni-eu-1"

[targets.production]
mode = "self-managed"
base_url = "https://gw.internal.acme.com"
environment = "Production"
gateway_name = "prod-k8s-omni"
```

`DONKEY_TARGET` selects the profile; `GatewayTarget.from_env()` resolves it
into the object above.

## One object, three verbs — not one deploy

Application code that applies policies directly to a shared gateway has taken
the platform team's job, and that's the review comment that gets an SDK
rejected. So the `Governance` object does not have a runtime `apply()`. It has
three verbs, at three different trust levels:

| Verb | Target | Who runs it | What it does |
|---|---|---|---|
| `simulate()` | local | developer, laptop | Starts an ephemeral local Omni Gateway, applies the config, returns a live `base_url`. Nothing shared is touched. |
| `export()` | sandbox, prod | developer, laptop | Compiles the object into a `donkey.yaml` fragment (see [Scan & publish](/publishing)). Writes a file. Touches nothing. |
| `resolve()` | sandbox, prod | agent process, runtime | **Read-only.** Looks up the already-provisioned gateway route, verifies the expected policies are actually applied, returns the `base_url`. Raises `GovernanceDrift` if reality does not match the declaration. |

There is deliberately **no `apply()` on the runtime object.** Applying to
sandbox and production goes through `donkey apply` in CI, against the
reviewed spec, under platform-controlled credentials, filtered by a policy
allow-list. The lifecycle is linear:

```text
agent code declares Governance
   → export()  → donkey.yaml   → PR review
   → CI: donkey plan      → posted as PR comment
   → merge: donkey apply  → gateway provisioned
   → runtime: resolve()         → verifies + returns URL
```

`resolve()` is what makes this feel like one object rather than a bureaucratic
downgrade: the developer writes one `Governance` object, and at runtime it
*checks* rather than *mutates*. A mismatch fails loudly at startup instead of
silently running ungoverned — a genuinely better property than blind
application.

<Callout type="warning">
  **Escape hatch.** `Governance.apply(target, i_am_the_platform_team=True)`
  exists for platform teams automating their own gateways. The kwarg name is
  deliberately explicit, the connected app must hold write scopes it does not
  have by default, and every use is logged at `WARNING`.
</Callout>

## Local ≠ sandbox (this matters)

The difference between local and sandbox/prod is not just the URL. Local Mode
gateways are configured by declarative YAML on disk and do not talk to the
control plane — anything control-plane-dependent is unavailable locally.

| Capability | Local Mode | Connected Mode |
|---|---|---|
| Routing, CORS, headers, TLS | yes | yes |
| Basic rate limiting / spike control | yes | yes |
| Custom WASM (PDK) policies | yes | yes |
| SLA-based rate limiting, client-ID enforcement, contracts | **no** (needs API Manager client apps) | yes |
| **LLM Proxy** | **probably not — verify** | yes |
| **MCP Bridge** | **probably not — verify** (API Manager guided experience) | yes |
| Control-plane analytics, token usage reporting | no | yes |

If LLM Proxy and MCP Bridge turn out to be Connected-Mode-only — the single
most important thing verification has to confirm — `simulate()` still validates routing,
auth, rate limiting, custom policies, and request/response shape. Real value
for the dev loop. But LLM traffic is served by a **local mock proxy** the SDK
ships: an OpenAI-compatible stub that replays fixtures and simulates policy
rejections. It is labelled unambiguously in logs:

```text
LOCAL SIMULATION — LLM proxy is mocked, not a real gateway
```

Never let a developer believe they tested the real thing.

### Policies are not portable across modes

```python
class PolicyPortability(Enum):
    BOTH = "both"
    CONNECTED_ONLY = "connected_only"
    LOCAL_ONLY = "local_only"
    UNKNOWN = "unknown"
```

Before it starts, `simulate()` prints exactly which declared policies are
being skipped and why — loud, non-suppressible by default, and repeated in the
teardown summary:

```text
Starting local Omni Gateway (target: local)
  applied  cors                            1.0.0
  applied  rate-limiting                   1.3.0
  applied  acme-custom-redaction           0.2.0  (WASM)
  SKIPPED  rate-limiting-sla-based         1.4.0  connected-mode only (needs API Manager client apps)
  SKIPPED  prompt-injection-protection     1.0.0  connected-mode only
  ! 2 of 5 policies are not exercised locally. Local pass does not imply sandbox pass.
```

A silent skip here is the worst possible failure mode for this feature.

### Identity and secrets differ too

There is no connected app, no client credentials, and no Secrets Manager
locally. A `LocalCredentialShim` generates throwaway credentials and injects
them into both the gateway config and the SDK client, so `${secret:...}`
references in the spec resolve to dev values from a gitignored
`.donkey-kit.local.toml`.

## `simulate()` — the local harness

```python
async with gov.simulate() as env:
    model = donkey.langgraph.chat_model("gpt-4o", gateway=env.gateway)
    tools = await donkey.tools.discover(domain="hr", gateway=env.gateway)
    agent = create_react_agent(model, tools.langgraph())
    result = await agent.ainvoke({"messages": [("user", "…")]})
assert env.policy_events("rate-limiting").count == 1
```

`env` exposes `gateway` (a `GatewayTarget` pointing at a dynamically-allocated
localhost port), `logs()`, and `policy_events(policy_name)` parsed from
gateway logs, so a test can assert a policy actually fired.

<Callout type="warning">
  **Docker is a hard dependency for this feature only.** It ships behind the
  optional `[local]` extra — the rest of the SDK works without it. Whether
  Local Mode itself requires a control-plane-issued registration/licence
  artifact (which would gate whether CI runners without an Anypoint org can run
  `simulate()` at all) is a verification item — see
  [Verification policy](/concepts/verification).
</Callout>

## MCP servers written in Python or TypeScript

Worth stating plainly: if you write an MCP server in your agent framework and
attach a `Governance` object, the SDK can put a gateway in front of it
locally, and can generate the gateway configuration for sandbox and
production. **It cannot deploy the server itself to sandbox or production.**
CloudHub 2.0 runs Mule applications; there is no MuleSoft-hosted runtime for a
Python or TypeScript process. See [Tool access](/tool-access) for the
discovery/binding side of the same server.

| | Local | Sandbox / Prod |
|---|---|---|
| The MCP server process | SDK runs it in docker-compose | **Your own platform** — K8s, Cloud Run, Lambda, ECS |
| The gateway in front of it | SDK spins up local Omni Gateway | SDK exports config; CI applies it |
| Upstream URL in the config | container DNS name | user-supplied, from your deployment |

To narrow that gap, `donkey-kit export --with-runtime` may emit a Dockerfile
and a plain Kubernetes manifest as a starting point — a convenience, never a
deployment platform. The SDK does not become a deployment orchestrator.
